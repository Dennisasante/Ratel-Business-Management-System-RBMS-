# RBMS v5 — WordPress/WooCommerce Integration, Booking Widget, and Custom Wig Requests

Scoped against the actual codebase (Spring Boot + Postgres/Flyway backend, Next.js frontend, multi-tenant via `business_id`) and the actual pilot site, `chelleluxuryhair.com` (WordPress 7, WooCommerce 11, Elementor, currently running LatePoint Pro for bookings — confirmed via the live site, not assumed).

**Confirmed decisions (final, not open questions) — correct me if wrong:**
- **LatePoint gets fully replaced**, not synced with. Its services (Ponytails, Closure Install, Frontal Install, Lace Customization, Sew In) get recreated as RBMS `service_catalog` items; its `/book-a-service/` and `/my-bookings/` pages get repointed at the new embed.
- **A booking becomes a real `service_order` immediately**, not a separate approval queue — it lands as `RECEIVED` with `scheduled_at` set, so it shows up in the existing Service Orders list/calendar/status pipeline you already have, instead of a second parallel system.
- **No customer account/login system.** Reschedule/cancel happens via a unique "manage your booking" link (token in the URL) sent in the confirmation email — same idea as most modern booking tools, and far less to build than replicating LatePoint's email/password login.
- **Payment at booking time is optional, not forced.** The widget always offers "Pay now with Paystack," but a booking can be confirmed without paying (pay in person) — matches how salon bookings actually work; you'll see `payment_status` either way.
- **Per-business Paystack/WooCommerce credentials are encrypted at rest** (new `ENCRYPTION_KEY` env var, AES-GCM via a JPA attribute converter), not stored as plain text. These are live payment credentials for potentially many separate businesses sharing one database — meaningfully more sensitive than anything currently stored (JWT secret, DB password are env vars, never in the DB at all).
- **WooCommerce webhook registration is automatic.** When you hit "Test connection" in the Integrations tab, RBMS calls the WooCommerce REST API itself to create the webhook — you never touch wp-admin.
- **Not every service is bookable online by default.** `service_catalog` gets a `bookable_online` flag, off by default, so a business can offer something in-person-only without it showing up in the public widget.
- **WhatsApp automation (system sends a message with no human tapping anything) is out of scope for V1.** That needs a Meta-verified WhatsApp Business Platform number per vendor, which none of yours are confirmed to have yet. V1 ships reliable email everywhere a notification is needed, plus `wa.me` deep-link buttons in RBMS for one-tap staff-initiated WhatsApp messages (new booking → notify yourself, order ready → notify customer, quote ready → notify customer). Upgrading a specific vendor to full automation later is additive, not a rebuild.
- **Feature gating only applies to what's built here** (booking widget, WooCommerce sync, custom wig requests) — existing core functionality isn't retroactively restricted for anyone already paying for a plan.
- **Stock sync is one-directional**: RBMS is always the source of truth; a stock change from any path (POS sale, adjustment, PO received, a WooCommerce order coming in) pushes the new quantity out to WooCommerce. RBMS never reads stock back from WooCommerce.
- **Product/variant sync starts with simple products only.** WooCommerce variable products (the "Select options," multiple sizes/colors you already sell) are a stretch goal — pushing a new simple product with one price/photo from RBMS is V1; full variant parity is a later pass.
- **No migration of existing LatePoint booking history.** This is a forward-only cutover — old bookings stay in LatePoint's own tables, untouched, just not fed into RBMS.

## 1. Database — `V12__integrations_booking_woocommerce_custom_wigs.sql`

```sql
-- One settings row per business — Paystack keys are the CLIENT's own account
-- (their customers pay them directly), completely separate from the platform's
-- own PAYSTACK_SECRET_KEY/PUBLIC_KEY used for RBMS subscription billing.
CREATE TABLE business_integrations (
    id                          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    business_id                 UUID NOT NULL UNIQUE REFERENCES businesses(id) ON DELETE CASCADE,
    paystack_public_key         TEXT,
    paystack_secret_key         TEXT,   -- encrypted at rest, see confirmed decisions
    woocommerce_site_url        TEXT,
    woocommerce_consumer_key    TEXT,
    woocommerce_consumer_secret TEXT,   -- encrypted at rest
    woocommerce_webhook_secret  TEXT,   -- generated by RBMS when the webhook is registered, verifies inbound payloads
    whatsapp_notify_number      VARCHAR(20),  -- E.164, e.g. +233550995080 — where "new booking" pings go
    test_mode                   BOOLEAN NOT NULL DEFAULT FALSE,
    created_at                  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at                  TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE service_catalog ADD COLUMN bookable_online BOOLEAN NOT NULL DEFAULT FALSE;

CREATE TABLE bookings (
    id                  UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    business_id         UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
    booking_number      BIGSERIAL,
    service_order_id    UUID NOT NULL REFERENCES service_orders(id) ON DELETE CASCADE, -- the real record staff work from
    customer_name       VARCHAR(150) NOT NULL,
    customer_email      VARCHAR(255) NOT NULL,
    customer_whatsapp   VARCHAR(20) NOT NULL,   -- mandatory, per your requirement
    manage_token        VARCHAR(64) NOT NULL UNIQUE,  -- reschedule/cancel link, no login needed
    payment_status      VARCHAR(20) NOT NULL DEFAULT 'UNPAID', -- UNPAID, PAID, FAILED
    paystack_reference  VARCHAR(100) UNIQUE,    -- idempotency key, same pattern as subscription_payments
    is_test             BOOLEAN NOT NULL DEFAULT FALSE, -- created while business_integrations.test_mode was on
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_bookings_business_id ON bookings(business_id);
CREATE INDEX idx_bookings_service_order_id ON bookings(service_order_id);

-- E-commerce orders coming in from WooCommerce. Deliberately not reusing `sales`
-- (a Sale is an instant, already-complete POS transaction with no status
-- pipeline) — a web order needs Received → Processing → Ready tracking, which
-- would otherwise mean bolting an evolving status onto a core entity every
-- report/receipt already depends on.
CREATE TABLE ecommerce_orders (
    id                   UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    business_id          UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
    woo_order_id         BIGINT NOT NULL,
    order_number         VARCHAR(50) NOT NULL,  -- WooCommerce's own order number, for the customer's reference
    status               VARCHAR(20) NOT NULL DEFAULT 'RECEIVED', -- RECEIVED, PROCESSING, READY, COMPLETED, CANCELLED
    customer_name        VARCHAR(150),
    customer_email       VARCHAR(255),
    customer_phone       VARCHAR(20),
    total_amount         NUMERIC(12,2) NOT NULL,
    currency             VARCHAR(10) NOT NULL DEFAULT 'GHS',
    raw_payload          JSONB,   -- full webhook body, kept for debugging/support without re-fetching from Woo
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_ecommerce_orders_business_woo UNIQUE (business_id, woo_order_id)
);

CREATE TABLE ecommerce_order_items (
    id                    UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    ecommerce_order_id    UUID NOT NULL REFERENCES ecommerce_orders(id) ON DELETE CASCADE,
    product_name          VARCHAR(200) NOT NULL,  -- snapshotted, same reasoning as sale_items
    product_id            UUID REFERENCES products(id) ON DELETE SET NULL, -- matched by SKU if possible, else null
    quantity              INT NOT NULL,
    unit_price             NUMERIC(12,2) NOT NULL
);

CREATE INDEX idx_ecommerce_orders_business_id ON ecommerce_orders(business_id);

-- Products get a link to their WooCommerce counterpart once pushed.
ALTER TABLE products ADD COLUMN woo_product_id BIGINT;
ALTER TABLE products ADD COLUMN publish_to_website BOOLEAN NOT NULL DEFAULT FALSE;

-- Custom wig configurator: business-defined attributes (Length, Color, Texture...)
-- each with priced options, snapshotted onto every request so editing an
-- attribute later never rewrites history (same reasoning as everything else
-- in this app that snapshots a name/price at the moment it mattered).
CREATE TABLE custom_item_attributes (
    id           UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    business_id  UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
    name         VARCHAR(100) NOT NULL,   -- "Length", "Color", "Texture", "Lace Type"
    sort_order   INT NOT NULL DEFAULT 0
);

CREATE TABLE custom_item_attribute_options (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    attribute_id    UUID NOT NULL REFERENCES custom_item_attributes(id) ON DELETE CASCADE,
    label           VARCHAR(100) NOT NULL,  -- "14 inches", "Jet Black", "Straight"
    price_modifier  NUMERIC(12,2) NOT NULL DEFAULT 0,
    sort_order      INT NOT NULL DEFAULT 0
);

CREATE TABLE custom_wig_requests (
    id                     UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    business_id            UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
    request_number         BIGSERIAL,
    customer_name          VARCHAR(150) NOT NULL,
    customer_email         VARCHAR(255) NOT NULL,
    customer_whatsapp      VARCHAR(20) NOT NULL,
    selections             JSONB NOT NULL,  -- [{attributeName, optionLabel, priceModifier}, ...] snapshotted at submission
    estimated_price        NUMERIC(12,2) NOT NULL,  -- live-computed total shown to the customer at submission time
    inspiration_photo_url  TEXT,
    notes                  TEXT,
    status                 VARCHAR(20) NOT NULL DEFAULT 'SUBMITTED', -- SUBMITTED, QUOTED, ACCEPTED, DECLINED
    final_price            NUMERIC(12,2),
    owner_message          TEXT,
    is_test                BOOLEAN NOT NULL DEFAULT FALSE,
    created_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at             TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_custom_item_attributes_business_id ON custom_item_attributes(business_id);
CREATE INDEX idx_custom_wig_requests_business_id ON custom_wig_requests(business_id);

-- Plan-based feature gating.
ALTER TABLE subscription_plans ADD COLUMN features TEXT[] NOT NULL DEFAULT '{}';
-- Feature codes used by the backend gate: BOOKING_WIDGET, WOOCOMMERCE_SYNC, CUSTOM_WIG_REQUESTS
```

## 2. Backend

New packages, same `entity`/`repository`/`service`/`controller`/`dto` split as everywhere else:

**Integrations**
- `entity/BusinessIntegrations.java` + an `AttributeConverter` (`EncryptedStringConverter`) applied to the three secret fields via `@Convert`
- `service/BusinessIntegrationsService.java` — get/update; `testPaystackConnection()` (calls Paystack's own `/transaction/verify` style ping, or simplest: attempt a trivial authenticated GET against Paystack's API with the given secret key and report success/failure); `testWooCommerceConnection()` (GET `/wp-json/wc/v3/system_status` with the given keys, and on success **register the webhook**: POST `/wp-json/wc/v3/webhooks` for `order.created`/`order.updated`, pointed at `POST /api/webhooks/woocommerce/{businessId}`, storing the secret Woo returns for signature verification)
- `controller/BusinessIntegrationsController.java` — `GET/PUT /api/integrations`, `POST /api/integrations/test-paystack`, `POST /api/integrations/test-woocommerce`, all `@PreAuthorize("hasRole('OWNER')")`, same reasoning as billing

**Booking**
- `entity/Booking.java`
- `service/BookingService.java` — `createBooking(businessId, request)`: validates the `service_catalog_id` is `bookable_online`, creates the linked `ServiceOrder` (status `RECEIVED`, `scheduled_at` from the request), generates `manage_token`, sends confirmation email, returns the token/reference; `startPayment(token)` → reuses `PaystackService` but constructed per-call with the **business's own** keys (not the platform's) via `BusinessIntegrations`; `verifyPayment(reference)` — identical idempotency pattern to `BillingService.verifyPayment` (unique `paystack_reference`, re-verify server-side, never trust the client); `reschedule(token, newTime)`, `cancel(token)` — both look up by `manage_token`, update the linked `ServiceOrder`
- `controller/PublicBookingController.java` — `@RequestMapping("/api/public/bookings")`, **no JWT**, business identified by a `businessId` path/query param the widget already carries (this is public-facing intentionally — it's what makes the embed copy-paste simple): `GET /services?businessId=` (bookable-online catalog for the picker), `POST /` (create), `POST /{token}/pay`, `POST /verify`, `GET /{token}`, `PATCH /{token}/reschedule`, `DELETE /{token}` (cancel)
- Read-only rate limiting reuses the existing `RateLimiterService` pattern (already used on login/reset) — a public, unauthenticated POST endpoint needs it far more than an internal one

**WooCommerce**
- `entity/EcommerceOrder.java`, `entity/EcommerceOrderItem.java`
- `service/WooCommerceSyncService.java` — `pushProduct(product)` (create/update via REST API, matching by `woo_product_id` if already linked, category created-if-missing by name match), `pushStockChange(product)` (called from the existing `ProductService.adjustStock` path — one new call at the end of an already-existing method, not a new stock-mutation path), `handleIncomingOrder(businessId, payload)` (webhook target: verify signature against the stored per-business webhook secret, upsert by `woo_order_id`, snapshot line items, send the "we've received your order" email)
- `controller/EcommerceOrderController.java` — `GET /api/ecommerce-orders`, `PATCH /{id}/status` (RECEIVED→PROCESSING→READY→COMPLETED, same fixed-line-with-one-branch pattern as Service Orders' own status control, CANCELLED branches off any non-terminal state) — status change fires the customer email + surfaces a `wa.me` link in the response for the "notify customer" button
- `controller/WooCommerceWebhookController.java` — `POST /api/webhooks/woocommerce/{businessId}`, public, signature-verified

**Custom wig requests**
- `entity/CustomItemAttribute.java`, `entity/CustomItemAttributeOption.java`, `entity/CustomWigRequest.java`
- `service/CustomItemAttributeService.java` — CRUD for the attribute/option pricing rules (owner-configured, mirrors `ServiceTypeService`'s shape)
- `service/CustomWigRequestService.java` — `submit()` (public, computes `estimated_price` server-side from current option prices — never trust a client-computed total, even though the widget also shows a live estimate for UX), `quote(id, finalPrice, message)` (owner action, sends the customer an email with the quote and returns a `wa.me` link pre-filled with the same message), `decline(id, message)`
- `controller/CustomItemAttributeController.java`, `controller/CustomWigRequestController.java`, `controller/PublicCustomWigController.java` (public submission + inspiration photo upload, same multipart pattern as `ServiceOrderPhotoService`)

**Feature gating**
- `service/PlanFeatureService.java` — `requireFeature(businessId, "WOOCOMMERCE_SYNC")` throwing a 403 with "Upgrade your plan to use this" if the business's current plan (or lack of one) doesn't include it; called at the top of every controller method introduced above except the public-facing ones (a business without the feature shouldn't be able to receive public bookings at all — `PublicBookingController` checks it too, just returns a generic "booking isn't available for this business" instead of a plan-upsell message, since the person hitting that endpoint is a customer, not the owner)

**WhatsApp**
- `service/WhatsAppLinkService.java` — one static helper, `buildLink(phoneNumber, message)` → URL-encodes and returns `https://wa.me/<e164>?text=...`. No API keys, no external calls, nothing to configure beyond the phone number already on `business_integrations.whatsapp_notify_number`. Used wherever a notification moment exists (new booking, order status change, wig quote ready).

## 3. Frontend

- `app/dashboard/profile/integrations/` (or a new tab on the existing Profile page) — Paystack public/secret key fields, WooCommerce site URL + consumer key/secret, "Test connection" buttons (own pending state each, per your standard), Test Mode toggle with a clear "N test bookings/orders — clear them" action once you're done validating a client's setup
- `app/dashboard/bookings/` — list (mirrors Service Orders' list shape, filtered to ones with a linked booking), booking detail shows payment status + the customer's WhatsApp/email, a "Message via WhatsApp" button using `WhatsAppLinkService`'s link
- `app/dashboard/service-orders` — `bookable_online` toggle added to the existing catalog manager
- `public/widgets/booking-widget.js` (or served from a dedicated route) — the actual embeddable script: service picker (only `bookable_online` items), date/time picker, name/email/WhatsApp fields (WhatsApp marked required), optional "Pay now" step using Paystack Inline JS exactly like the Billing page already does (just pointed at the business's own public key instead of the platform's), confirmation screen with the manage link. A `<script src="...booking-widget.js" data-business-id="...">` snippet is what you paste into the WordPress HTML block — nothing else to configure per site.
- `app/booking/manage/[token]/` — the reschedule/cancel page the email link points to, outside `app/dashboard/` (public, no auth) — same reasoning as the receipt pages already living outside the dashboard shell
- `app/dashboard/ecommerce-orders/` — list with the status pipeline control, customer contact shown, "Notify customer" WhatsApp button
- `app/dashboard/custom-wig-requests/` — inbox (Submitted/Quoted/Accepted/Declined filter chips), detail view showing the selections + computed estimate + inspiration photo, quote form (final price + message), "Send quote" button that emails the customer and surfaces the WhatsApp link
- `app/dashboard/custom-wig-requests/attributes/` — pricing rules manager (add attribute, add options with a price modifier each) — same list/add/rename/remove shape as Service Types
- `public/widgets/custom-wig-widget.js` — attribute dropdowns building a live running total client-side (server recomputes on submit, per the "never trust a client total" rule above), inspiration photo upload, submit
- Plan upsell banner — same visual treatment as the read-only banner (persistent bar), accent-toned instead of danger-toned, shown on `bookings`/`ecommerce-orders`/`custom-wig-requests` pages when the business's plan doesn't include that feature, linking to `/dashboard/billing`
- Platform side: `subscription_plans` edit form (already built) gets a features multi-select (checkboxes for the three new feature codes)

## 4. Explicitly out of scope here
- WhatsApp Cloud API automation — deferred per vendor until they're Meta-verified; V1 is email + `wa.me` links throughout
- Migrating LatePoint's existing booking history into RBMS
- WooCommerce variable products (multi-attribute variants) — V1 pushes simple products only
- Reading stock back from WooCommerce, or any two-way stock conflict resolution
- A customer-facing account/login system — magic links replace it entirely
- Multi-currency WooCommerce sync (GHS only, same assumption as the billing spec)

## 5. Suggested build order
1. Migration V12 + entities/repos across all five areas (foundation everything else sits on) + the `EncryptedStringConverter`
2. `BusinessIntegrations` backend + frontend (Integrations tab, Test Mode, Test Connection buttons) — isolated and testable against your real Paystack test keys and a real WooCommerce site before anything depends on it
3. Plan-based feature gating (small, unblocks demonstrating tiered plans early)
4. Booking backend (public API, service-order creation, per-business Paystack checkout, magic-link manage) — tested against Chelle Luxury Hair's real recreated services
5. Booking embed widget + the `/booking/manage/[token]` page, pasted into a real (or staging) page on the pilot site
6. WooCommerce sync backend (webhook intake, product push, stock push) — registered against the real site's WooCommerce API in test mode
7. E-commerce order management UI + customer notifications
8. Custom wig configurator backend (attributes/pricing, request/quote)
9. Custom wig configurator embed widget + RBMS review/quote UI
10. WhatsApp `wa.me` links wired into every notification touchpoint built above
